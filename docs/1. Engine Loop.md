# 1. Engine Loop

Purpose: isolated reference for Pixl engine loop design discussion. This captures agreed direction and implementation notes for future rewrite work.


Status: Aligned / extracted reference

### User Concern

Even with an almost empty game containing only a player and no meaningful collision work, a 60 FPS target can show frequent 1-2 FPS drops. That suggests loop reliability/frame pacing rather than raw gameplay workload.

### Current Pixl Approach

Pixl currently uses a fixed simulation step and variable render cadence on both native macOS and Web:

Sources:

- `Sources/PlatformMac/Runtime.swift:40` defines native fixed step.
- `Sources/PlatformMac/Runtime.swift:121` runs the native frame loop.
- `Sources/PlatformWeb/Runtime.swift:24` defines web fixed step.
- `Sources/PlatformWeb/Runtime.swift:56` runs the web frame loop.
- `Sources/Pixl/Game.swift:135` runs one simulation update.
- `Sources/Pixl/Game.swift:265` rebuilds render commands/batches.

```swift
accumulatedTime += max(rawDeltaSeconds, 0)

while accumulatedTime >= fixedTimeStep {
    game.update(delta: fixedTimeStep, input: inputState)
    audio.playSounds(game.drainSounds())
    accumulatedTime -= fixedTimeStep
}

renderer.draw(game: game)
```

The fixed step is derived from `preferredFps`, defaulting to 60 FPS:

```swift
var fixedTimeStep: Double {
    guard game.preferredFps > 0 else {
        return 1.0 / 60.0
    }

    return 1.0 / game.preferredFps
}
```

Observed current implications:

- Simulation delta is stable when updates run.
- Rendering is not interpolated between previous/current simulation states.
- If a frame arrives late, the loop may run multiple simulation updates before one draw.
- There is no visible accumulator clamp, max-update cap, panic/drop policy, or timing smoothing.
- Mac uses `MTKView.draw(in:)` as the render callback and sets `preferredFramesPerSecond`.
- Web uses `requestAnimationFrame`.
- Both platforms depend on the host display/runtime callback for cadence.

### Current Per-Tick Work

One `game.update` currently performs, at minimum:

- input/debug/time-scale handling
- frame event preparation
- entity `onUpdate` iteration
- system updates before post-collision
- movement/collision application
- contact detection
- collision callback dispatch
- system updates from post-collision onward
- camera update
- render frame rebuild
- render command sort
- render batch generation

Even an "empty" game is not only drawing one sprite; it still runs the whole pipeline.

### Current Hypotheses For 1-2 FPS Drops

These are discussion hypotheses, not measured conclusions:

1. Display callback jitter: `MTKView`/display scheduling may not deliver perfectly spaced 16.666 ms callbacks.
2. Accumulator threshold sensitivity: tiny timing variance can cause occasional skipped update or double update patterns.
3. No interpolation: render cadence variation is visually exposed instead of hidden by interpolation.
4. No clamp/cap: after any hitch, the loop can spend the next draw catching up.
5. Render rebuild every tick: frame commands, sort, and batches are regenerated after every simulation update.
6. Allocation/copy churn: arrays, sorted command rebuilds, existential entity calls, and collision temporary arrays can create jitter even if average cost is low.
7. Main-thread coupling: input, update, audio event dispatch, frame rebuild, and render submission all share the main actor/native callback path.

### Discussion Targets

- Decide whether Pixl should keep fixed-step simulation.
- Decide how rendering should behave between simulation ticks.
- Decide whether frame pacing should target deterministic simulation, visual smoothness, lowest latency, or configurable profiles.
- Decide what metrics are mandatory before rewrite decisions.
- Decide what the engine guarantees to game code: exact fixed delta, max updates per frame, dropped time behavior, interpolation alpha, etc.
- Discuss moving accumulator, clamping, interpolation, and pacing into Pixl instead of duplicating that policy in each platform.

### Preferred Direction Under Discussion

The platform layer should ideally own only platform time capture and presentation callbacks:

```swift
game.update(rawDelta)
renderer.draw(game, in: view)
```

Then Pixl owns the loop policy:

- receive raw platform delta
- clamp pathological raw delta values
- accumulate elapsed time
- run zero or more fixed simulation ticks
- cap catch-up work
- compute interpolation alpha
- prepare render-facing state

This keeps gameplay easier to reason about because game simulation remains single-threaded and fixed-step, while each platform adapter avoids reimplementing core timing rules.

Important naming note: this likely means splitting today's `game.update(delta:)` into two conceptual layers:

- public/platform-facing frame update: accepts raw frame delta
- internal simulation tick: accepts fixed simulation delta

Example shape:

```swift
public mutating func update(rawDelta: Double, input: Input) {
    let frameStart = clock.now()
    let clampedDelta = min(max(rawDelta, 0), loop.maximumFrameDelta)

    if diagnostics.isVisible {
        diagnostics.beginFrame(rawDelta: rawDelta, clampedDelta: clampedDelta)
    }

    loop.accumulator += clampedDelta

    snapshotPreviousPresentationState()

    var steps = 0
    while loop.accumulator >= loop.fixedDelta && steps < loop.maximumSimulationStepsPerFrame {
        simulateFixedStep(delta: loop.fixedDelta, input: input)
        loop.accumulator -= loop.fixedDelta
        steps += 1
    }

    if steps == loop.maximumSimulationStepsPerFrame && loop.accumulator >= loop.fixedDelta {
        loop.droppedTime += loop.accumulator
        loop.accumulator = 0
    }

    let alpha = loop.accumulator / loop.fixedDelta
    prepareRenderState(interpolationAlpha: alpha)

    if diagnostics.isVisible {
        diagnostics.endFrame(
            steps: steps,
            accumulator: loop.accumulator,
            interpolationAlpha: alpha,
            elapsed: clock.now() - frameStart
        )
    }
}
```

Teaching note: `rawDelta` is the platform's observed time since the last frame callback. `fixedDelta` is the engine's chosen simulation step, such as `1.0 / 60.0`. The platform measures real time; the engine decides how much of that real time becomes simulation work.

Time source rule:

- Use monotonic time for frame deltas.
- Do not use wall-clock time for gameplay deltas.

Monotonic time means a timer that only moves forward. Wall-clock time can jump if the user changes system time, time zone rules change, sleep/wake adjusts the clock, or the OS corrects time. Frame pacing needs elapsed duration, not calendar time.

### Clamping

Clamping means forcing a value into a safe range.

For the loop, there are two separate clamps:

1. Raw delta clamp.
   If the platform says `0.75` seconds passed, the engine may treat it as only `0.10` seconds. This handles pauses, breakpoints, window drags, OS stalls, or tab sleep.
2. Simulation step cap.
   If accumulated time would require 20 fixed simulation ticks before drawing again, the engine may run only 4 ticks, drop the remaining accumulated time, and draw.

The problem this avoids: if one frame is slow, the next frame may try to run extra simulation ticks to catch up. Those extra ticks make that next frame slow too, which creates more catch-up work. Without a cap, the game can get stuck spending most frames catching up instead of drawing. This is what some game-dev writing calls "spiral of death"; in this doc, prefer saying "unbounded catch-up loop."

### Interpolation

Interpolation means producing an in-between render value from two known simulation states.

If simulation runs at fixed 60 Hz, state only changes every `16.666ms`. But display callbacks may arrive slightly before or after that exact cadence. Rendering only the latest fixed state can look uneven even when the simulation is correct.

Example:

```swift
let alpha = accumulator / fixedDelta
let renderX = previousX + ((currentX - previousX) * alpha)
```

If `alpha == 0`, render exactly the previous state.
If `alpha == 1`, render exactly the current state.
If `alpha == 0.5`, render halfway between them.

Likely interpolated values:

- transform position
- rotation
- scale
- camera position
- visual-only animation state

Values that should usually not be interpolated:

- entity IDs
- health/lives/scores
- collision/contact state
- spawn/despawn ownership
- gameplay decisions

The key design rule: fixed simulation remains authoritative. Interpolation is presentation only.

### How Engines Usually Expose This To Games

The game should usually not decide what to do with accumulator, clamp, dropped time, or interpolation policy every frame. The engine should own those rules and call game code at the right time.

Common model:

- fixed simulation callback: deterministic gameplay and physics
- variable frame callback: presentation-only animation, UI, debug, camera smoothing if desired
- render callback: draw from prepared/interpolated presentation state

Example engine-facing shape:

```swift
protocol GameScene {
    mutating func fixedUpdate(context: FixedUpdateContext)
    mutating func update(context: FrameUpdateContext)
    mutating func render(context: RenderContext)
}
```

The platform calls:

```swift
game.update(rawDelta)
renderer.draw(game, in: view)
```

The engine internally does:

```swift
func update(rawDelta: Double) {
    let clampedDelta = clamp(rawDelta)
    accumulator += clampedDelta

    while accumulator >= fixedDelta && steps < maxSteps {
        scene.fixedUpdate(context: .init(delta: fixedDelta))
        accumulator -= fixedDelta
        steps += 1
    }

    if accumulator still too large {
        dropRemainingCatchUpTime()
    }

    let alpha = accumulator / fixedDelta
    scene.update(context: .init(delta: clampedDelta, interpolationAlpha: alpha))
    prepareRenderState(alpha: alpha)
}
```

So a normal game says "move this enemy during fixed update" or "animate this menu during frame update." It does not need to know why the engine ran zero fixed ticks this frame, one fixed tick this frame, or four fixed ticks this frame.

Examples from established engines:

- Unity has a fixed-timestep callback for physics/gameplay-like work and a per-frame callback for frame-rate-dependent work.
- Godot separates physics processing from idle/frame processing.
- Many engines with physics call simulation in fixed substeps, then render the latest/interpolated state.

The API lesson for Pixl: expose time domains, not timing machinery. Game code should choose "this belongs to fixed gameplay time" or "this belongs to presentation/frame time." Pixl should handle the accumulator, clamping, step cap, and interpolation details.

Optional advanced escape hatches:

- diagnostics can report dropped/clamped time
- systems can subscribe to pause/resume or large-hitch events
- a game can opt into real-time timers for UI/network/audio-style needs

Default rule: gameplay uses simulation time only.

Input sampling note: detailed input API design belongs in the Input section, but the loop still needs one policy decision: when input becomes visible to fixed simulation. Simple default is to snapshot input once per platform frame and reuse that snapshot for every fixed tick run during that frame. More advanced input can queue timestamped events and consume them per fixed tick.

### Lifecycle Order

The engine should define one stable order. This matters because deterministic behavior depends on systems running in the same order each tick.

Proposed order:

```text
platform frame callback
read or receive input snapshot
engine update(rawDelta)
  clamp rawDelta
  accumulate clampedDelta
  repeat fixed ticks while needed/allowed
    fixedUpdate
    collision / physics
    postCollision
    apply lifecycle changes
  frameUpdate / presentation update
  prepare interpolated render state
renderer.draw
```

Teaching note: if collision sometimes runs before entity updates and sometimes after, bugs become difficult to reason about. A fixed lifecycle order makes game behavior predictable and testable.

### Pause, Resume, And Large Hitches

Pause policy is part of loop design because pausing affects time accumulation.

Cases to support:

- app loses focus
- window is dragged/resized
- platform pauses/backgrounds the app
- browser tab sleeps
- debugger breakpoint
- game opens a pause menu
- game programmatically pauses gameplay but keeps UI alive

Useful engine states:

```swift
enum RunState {
    case running
    case gameplayPaused
    case suspended
}
```

Possible policy:

- `running`: fixed simulation, frame update, and render all run.
- `gameplayPaused`: fixed simulation does not run; frame update/render can run for menus, UI, debug overlay, and pause animations.
- `suspended`: no simulation; on resume, discard accumulated time so the game does not try to catch up all missed time.

The engine should provide default policies, but games should be able to control pause state intentionally:

```swift
game.pauseGameplay()
game.resumeGameplay()
game.suspend()
game.resume(discardElapsedTime: true)
```

Open design question: should platform focus loss automatically pause gameplay, or should the game decide?

### Randomness And Determinism

Randomness can be game-owned, but the engine should provide a deterministic-friendly path.

If gameplay uses random numbers, replay/tests need the same random sequence each run. That means random generation used by gameplay should be seeded and part of game/simulation state.

Rule of thumb:

- Gameplay random: seeded, deterministic, owned by game or engine simulation state.
- Presentation random: can be independent, but must not affect gameplay decisions.

The engine does not need to force every game to use its RNG, but it should make the deterministic option easy.

### Floating Point And Determinism

Swift does not automatically guarantee identical floating-point results across every CPU, compiler mode, and platform target.

For normal Pixl goals, `Double` is fine and usually preferable for engine math simplicity and precision. Switching to `Float` does not make determinism magically better; it mainly reduces precision and may match GPU data better.

The practical rule:

- Use fixed timestep first. That removes the biggest source of nondeterminism.
- Avoid gameplay depending on tiny floating-point threshold differences.
- Use tolerances for comparisons where appropriate.
- If exact cross-platform replay becomes a hard requirement later, consider stricter numeric rules or fixed-point math for specific systems.

Current assumption: deterministic enough per platform/build is acceptable; exact Mac-vs-Web identical replay is not a section 1 requirement unless explicitly decided later.

### Avoiding CPU/GPU Blocking

The game loop should not wait for GPU work to finish during normal frames. The CPU should prepare commands, submit them, and continue on the next frame.

Things that can accidentally block:

- reading pixels back from the GPU
- waiting for command buffer completion
- reusing a buffer that the GPU is still reading
- creating/uploading large textures during gameplay
- compiling pipeline/shader state during gameplay
- running too many in-flight frames without backpressure

Engine direction:

- Use double/triple-buffered dynamic GPU resources.
- Keep a small number of frames in flight.
- Write this frame's dynamic data into a buffer region not currently used by the GPU.
- Load textures/pipelines up front or asynchronously outside hot gameplay frames.
- Never call synchronous GPU wait APIs in normal render path.
- Use debug-only GPU waits when explicitly profiling or validating.

Teaching note: CPU and GPU run asynchronously. Good render code keeps both busy without forcing either side to wait for the other.

### Frame Timing Instrumentation

Frame timing instrumentation means recording enough per-frame timing data to distinguish "the engine is slow" from "the platform callback arrived late" from "the loop did too much catch-up work."

Useful counters/timings:

- raw platform delta: time between display callbacks
- clamped delta: raw delta after engine safety limits
- accumulator before/after update
- simulation step count this frame
- update CPU time
- render-prep CPU time
- render-submit CPU time
- total frame CPU time
- interpolation alpha
- dropped/clamped time count
- max, average, percentile frame/update times over rolling windows

The important teaching point: FPS alone is a weak metric. A frame can "drop" because the callback came late, because CPU work exceeded budget, because the engine ran two catch-up ticks, because rendering blocked, or because measurement is averaged poorly. Instrumentation separates these causes.

Runtime impact goals:

- Diagnostics should be effectively zero-cost when disabled.
- If a debug overlay is hidden, do not collect rolling histories unless explicitly requested.
- Prefer simple counters and timestamps over allocations or string formatting in hot paths.
- Store samples in fixed-size ring buffers when visible.
- Build overlay text only when the overlay is drawn.
- Keep platform-specific GPU/Metal overlays optional; Pixl should have its own portable engine overlay.

Potential overlay values:

- FPS over short rolling window
- heartbeat graph showing recent frame timing as bars/line so frame drops are visible at a glance
- raw frame delta in milliseconds
- update time in milliseconds
- render preparation time in milliseconds
- render submission time in milliseconds
- average time spent in named phases, such as input, fixed update, collision, render prep, render submit, and custom game-defined phases
- simulation steps this frame
- interpolation alpha
- accumulator milliseconds
- clamped frame count
- dropped-time count
- visible entities/tiles
- render commands/primitives/batches

Overlay toggle should be runtime-accessible in-game.

Numerical values should use rolling windows where useful. Rapidly changing instantaneous FPS is not very helpful; a short rolling average plus a visual heartbeat graph makes stutters easier to see.

Custom phase timing should be possible, for example:

```swift
diagnostics.measure("Enemy AI") {
    updateEnemies()
}
```

When diagnostics are disabled, this API should avoid allocations and avoid expensive timing calls where possible.

### Options To Discuss

#### Fixed Step + Interpolated Render

Classic deterministic model:

```swift
while accumulator >= dt {
    previousState = currentState
    update(dt)
    accumulator -= dt
}

let alpha = accumulator / dt
render(interpolate(previousState, currentState, alpha))
```

Pros:

- deterministic simulation
- smoother visual motion under callback jitter
- easy replay/testing model

Costs:

- requires previous/current renderable state
- API must separate simulation state from presentation state
- interpolation policy needed per component/property

#### Fixed Step + Max Updates Per Frame

Add a catch-up cap:

```swift
let maxSteps = 4
var steps = 0

while accumulator >= dt && steps < maxSteps {
    update(dt)
    accumulator -= dt
    steps += 1
}

if steps == maxSteps {
    accumulator = 0
}
```

Pros:

- avoids an unbounded catch-up loop after a slow frame
- keeps render responsive after hitches

Costs:

- drops simulation time
- must define gameplay semantics of dropped time

#### Semi-Fixed Timestep

Use fixed steps for most updates, but consume leftover time up to a maximum. This can reduce visible jitter but weakens determinism.

#### Variable Timestep

Use actual `delta` for update. Usually worse for collision, physics, replay, and deterministic gameplay. Might remain useful for non-gameplay animation, UI, camera smoothing, or effects.

#### Decoupled Simulation And Render Threads

Run simulation on a dedicated loop/queue and render latest snapshot on display callback.

Pros:

- isolates display callback jitter from simulation
- can use spare cores

Costs:

- snapshot ownership complexity
- higher latency risk
- Swift data-race discipline required
- harder debugging
- Web support differs due browser threading constraints

### Parallelism Options

- Keep gameplay simulation single-threaded, but parallelize pure jobs inside a frame: broad-phase rebuild, particle simulation, animation sampling, visibility, render command preparation.
- Use double/triple-buffered immutable snapshots for render data.
- Use task/job system with frame-local arenas and deterministic join points.
- Avoid parallelizing arbitrary entity callbacks early; that requires strong API constraints around mutation, messaging, and ordering.

### GPU-Accelerated Options

Likely not useful for the core game loop itself. More relevant areas:

- GPU particle simulation.
- GPU sprite/instance expansion.
- GPU culling for very large worlds.
- Compute-based broad phase only for extreme entity counts, with high complexity and backend divergence.

Loop-facing GPU concern: do not block CPU waiting for GPU completion each frame. Rendering should be submitted asynchronously with bounded in-flight frames.

### Decisions

- Gameplay simulation should remain single-threaded for this area because it is easier to reason about.
- Parallelization and GPU acceleration are not part of the first loop design pass.
- Clamping and interpolation are agreed as concepts worth including in the rewrite direction.
- Accumulator, clamp, interpolation, and pacing policy should move into Pixl rather than live separately in each platform adapter.
