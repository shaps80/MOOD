### Discussion Notes

- Direction is not traditional ECS, but a "bag of things" model: entity authoring stays ergonomic, while hot storage is generated into cache-aware arrays.
- Stable ordering is required for entity-facing/gameplay-visible behavior.
- Reusable generic storage is desirable: the same handle/slot/order/metrics primitive should back generated stores for entities, components, collision bodies, renderables, timers, particles, or other dense engine collections.
- Storage should be organized around hot component capability where that improves system locality. Player and enemy can both participate in character movement storage, while bullets can participate in projectile movement storage.
- Concrete entity type storage alone is not enough for hot paths. Type-specific storage helps authoring/behavior, but movement/collision/render systems often need all matching component data together.
- Ordering policy belongs to generated storage group, not necessarily to concrete entity type. Character movement can be `.stable`; projectile movement can be `.unstable`.
- `@Component` on a protocol/type defines a storage-capable schema. The macro direction is SwiftData-inspired: user-authored stored properties are rewritten into generated accessors backed by store rows/columns.
- Game-facing code should not hand-write schemas such as `MovementSchema`; those are generated from component protocols/types.
- Key paths and schema metadata may be useful at setup, editor, tooling, reflection, and debug layers, but should not be the primary per-frame hot path unless measured and proven cheap enough.
- Generated hot-path access should use direct typed arrays, for example `columns.position[row]`, not `Any`/dictionary/key-path lookup per entity per frame.
- At the entity boundary, properties whose type conforms to a component protocol should be stored as separate component rows by default. This makes best-practice SOA storage the default.
- At the component boundary, nested component-capable values should be inline by default. Entity is the composition boundary; component is the data-layout boundary.
- Overrides can come later through options such as `@Component(.inline)`. Do not design override modes yet.
- A likely backing shape is columnar storage by generated property index: property `position` maps to a known typed column, and that column stores all position values for rows in that storage.
- Tombstone + append is the preferred stable ordering policy: removal marks rows inactive, insertion appends, and compaction happens at controlled boundaries such as level load/unload.
- Unstable storage can reuse rows/swap-remove for high-churn data such as bullets/projectiles/particles where stable order is not required.
- Generation counts remain useful. Stable stores may reuse less frequently, but unstable stores can reuse aggressively and need stale-handle protection.
- If storage fills before compaction, grow capacity, likely by doubling, continue, and report a developer-facing warning/metric.
- Storage metrics should mirror loop diagnostics: disabled by default, no release overhead unless explicitly enabled, with values such as active count, tombstone count, capacity, growth count, and fragmentation ratio.

Example sketch:

```swift
@Component
protocol Movable: Component {
    var position: Vec2 { get set }
    var velocity: Vec2 { get set }
}

protocol CharacterMovable: Movable {}
protocol ProjectileMovable: Movable {}

extension CharacterMovable {
    static var policy: OrderPolicy { .stable }
}

extension ProjectileMovable {
    static var policy: OrderPolicy { .unstable }
}

@Entity(CharacterMovable.self)
struct Player {}

@Entity(ProjectileMovable.self)
struct Bullet {}
```

Open concern: if `CharacterMovable` and `ProjectileMovable` are separate stores, systems that want all `Movable` objects need either two loops or a merged view. If they share one `Movable` store, one ordering policy may not fit all rows. This needs a clear grouping rule.

### Decisions

- Stable entity iteration order is required.
- Stable storage policy: remove now = tombstone, insert now = append, compact later at controlled maintenance boundaries.
- Initial compaction boundary: level load/unload is reasonable.
- Capacity policy: if storage fills, double capacity, continue, and report to developer diagnostics/console.
- Metrics should exist and be disabled by default/release, same spirit as loop diagnostics.
- Component storage is the likely hot-path direction; entities are composition/identity, components determine dense storage participation.
- Macro-generated accessors now exist in the PixlStore proof. Schema/world bundle generation is still represented manually in the test fixtures and should move into macros later.
- Pending final storage design.

## Frame-Scoped Entity Access

Preferred naming direction:

- `FrameEntity`: a frame-scoped live view of one entity.
- `FrameComponent`: a frame-scoped live view of one component row.

These names communicate lifecycle better than a generic "facade" term. The value looks like a normal struct in game code, but its generated getters/setters read and write engine storage.

Example target API:

```swift
if let enemy = world.entity(id: contact.target, as: Enemy.self) {
    enemy.health -= 10
}
```

The lookup returns `nil` when:

- the ID is dead
- the generation is stale
- the entity is not an `Enemy`
- required generated storage rows are missing

The returned value is valid only for the current frame/scope. Game code should store IDs/handles long-term, not `FrameEntity` or `FrameComponent` values.

### Invalidation

A frame-scoped value should carry a frame token:

```swift
struct EnemyFrameEntity {
    let id: EntityID
    let frameID: UInt64
    let storage: StorageAccess
}
```

Generated frame views should cache the row they point at when created. Because structural changes are deferred to a safe point, the row remains valid for the frame. This avoids doing handle-to-row lookup on every property access.

Generated getters should stay fast and read directly from typed columns. Generated setters should do the cheapest useful debug validation before writing, with the validation centralized in generated storage helpers rather than repeated as bespoke game-facing APIs:

```swift
var health: Int {
    get { _$storage.enemies.columns.health[_$row] }
    nonmutating set {
        _$storage.assertWritableFrame(_$frameID)
        _$storage.enemies.columns.health[_$row] = newValue
    }
}
```

Use a wide frame ID such as `UInt64`, not `UInt8`, to avoid quick wraparound making stale frame values appear valid again.

Debug behavior: if a game stores a frame-scoped entity and mutates it in a later frame, log/assert with a teaching message such as "FrameEntity used outside the frame it was created in. Store EntityID instead." Reads can remain unchecked for performance unless a debug mode explicitly asks for stricter validation.

### Query Shape

Avoid closure-first APIs for hot loops if possible. Prefer iterator/sequence-style APIs that produce frame-scoped live views:

```swift
for movable in world.entities.conforming(to: Movable.self) {
    movable.velocity.x += context.input.direction
}

for invader in world.entities.ofType(Invader.self) {
    swarmBounds.include(invader.position)
}
```

Fetching a specific entity should also be supported:

```swift
world.entity(id: contact.target, as: Enemy.self)?.health -= 10
```

Protocol-composition queries should hide physical storage grouping. Internally, `Movable` may map to several generated storage groups, but user code should ask for the protocol/capability it needs, not a named store.

## Mutation And Queues

Property mutation should be immediate. This is a core goal.

```swift
enemy.health -= 10
enemy.position.x += 2
```

Generated setters write directly to backing storage. This avoids the cumbersome pending-state pattern for ordinary gameplay values.

A queue is still useful for structural changes, even with stable order, tombstones, and append-only insertion.

Structural changes include:

- spawn entity
- despawn entity
- add component
- remove component
- change component storage group
- compact storage

Reason: structural changes can alter the set being iterated, component membership, query results, storage metrics, and lifecycle callbacks. Applying those immediately during iteration can create skipped rows, double visits, or inconsistent query views.

With the agreed stable policy:

- property set: immediate
- despawn: mark inactive or queue to mark inactive at safe point
- spawn: append immediately only if not currently iterating that affected query, otherwise queue to safe point
- compaction: controlled maintenance boundary, initially level load/unload

Open design choice: whether `despawn` marks inactive immediately or queues until the end of the current phase. Immediate inactive marking is possible with tombstones, but query semantics need to define whether the current iterator should still see that row later in the same pass.

## Macro Inference Rules

Agreed default direction:

- `@Component` on protocol/type defines a storage-capable schema.
- Entity-level properties whose type conforms to a component protocol are stored as separate component rows by default.
- Component-level nested component-capable values are inline by default.
- Entity is the composition boundary.
- Component is the data-layout boundary.
- Overrides can come later through options such as `@Component(.inline)`, but override modes are not designed yet.

Example:

```swift
@Component
struct Transform {
    var position: Vec2
    var rotation: Angle
}

@Component
struct Sprite {
    var transform: Transform
    var texture: TextureID
}

@Entity(Movable.self)
struct Player {
    var transform: Transform
    var sprite: Sprite
    var health: Int
}
```

Default interpretation:

- `Player.transform` becomes a separate generated `Transform` component row.
- `Player.sprite` becomes a separate generated `Sprite` component row.
- `Player.health` remains local/entity-specific storage unless made a component.
- `Sprite.transform` stays inline inside sprite storage because it is nested inside a component.

This makes SOA/default component storage the easy path while keeping component internals predictable.
